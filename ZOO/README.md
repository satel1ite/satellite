# Московский зоопарк — ERP-система

Консольное приложение на C++ для учёта животных и инвентаря зоопарка.

---

## Сборка и запуск

### Требования
- C++17 (GCC 9+, Clang 10+, MSVC 2019+)
- CMake 3.16+

### Через CMake

```bash
# Из корня проекта
mkdir build && cd build
cmake ..
cmake --build .

# Запуск
./ZooApp        # Linux / macOS
ZooApp.exe      # Windows
```

### Без CMake (g++)

```bash
g++ -std=c++17 -Wall -o ZooApp main.cpp && ./ZooApp
```

## Архитектура: принципы SOLID

### S — Single Responsibility
Каждый класс решает одну задачу:
- `VetClinic` — только медосмотр животного.
- `Zoo` — только управление коллекцией.
- `DIContainer` — только регистрация и разрешение зависимостей.
- `ReadInt` / `ReadString` — только валидированный ввод с консоли.

### O — Open/Closed
Иерархия открыта для расширения без изменения существующего кода. Чтобы добавить нового животного — достаточно унаследоваться от `Animal` (или `Herbo`/`Predator`). `Zoo` и `VetClinic` при этом не трогаются.

### L — Liskov Substitution
`Herbo` и `Predator` полностью подставляются вместо `Animal` в любом месте, где ожидается `Animal*`. `VetClinic::CheckHealth` работает с базовым `Animal*`, не зная о конкретном подтипе.

### I — Interface Segregation
Интерфейсы разделены по смыслу:
- `IAlive` — только `GetFood()`. Реализуют все живые: `Animal` и (в будущем) `Employee`.
- `IInventory` — только `GetNumber()`. Реализуют `Animal` и `Thing`, но **не** сотрудники.
- `IPlayerAnimal` — только `CanInteract()`. Реализует только `Herbo`, потому что только у травоядных есть понятие "доброта". Хищники физически не могут реализовать этот интерфейс — это запрет на уровне типов, а не условия в коде.

`Thing` реализует только `IInventory`: у вещей нет еды и они не бывают добрыми. Это пример ISP в действии — класс реализует ровно те интерфейсы, которые ему осмысленно подходят.

### D — Dependency Inversion
`Zoo` зависит от `IVetClinic*`, а не от конкретного `VetClinic`. Весь граф зависимостей строится в `main()` через `DIContainer` (composition root). Само приложение нигде не вызывает `new VetClinic()` напрямую.

## О решении по иерархии классов (обоснование)

Архитектор на кик-оффе предложил создать отдельные классы `Monkey`, `Rabbit`, `Tiger`, `Wolf`, `Table`, `Computer`. Я **осознанно отказался** от этого по следующим причинам:

**По животным:** в текущих требованиях у каждого вида нет своих уникальных полей. `Rabbit` от `Herbo` отличался бы только захардкоженным значением `food` — это не архитектурный смысл, а константа. Если в будущем у `Rabbit` появится `double jumpHeight`, а у `Wolf` — `string packRole`, вот тогда иерархия будет оправдана. Сейчас она была бы преждевременным усложнением.

**По вещам:** `Table` и `Computer` от базового `Thing` отличаются только названием. Смысл иерархии появится, когда у компьютера появятся свои поля (`string model`, `int ramGb`), а у стола — свои. Пока этого нет — плодить пустые подклассы нет смысла.

Ключевое правило: иерархия оправдана тогда, когда подклассы несут **уникальные данные или поведение**. Иначе это усложнение ради усложнения.

## DI-контейнер

Реализован продвинутый вариант (на 2 балла):
- Все сервисы наследуются от `IService`.
- Контейнер хранит: имя, фабричную функцию `IService*(DIContainer&)`, флаг singleton, кэшированный экземпляр.
- `Resolve("Zoo")` вызывает фабрику, которая сама запрашивает `Resolve("VetClinic")` — цепочка зависимостей разрешается автоматически.
- Весь граф объектов строится в одном месте (`SetupDI` в `main`) — composition root.

## Функциональность

| Пункт меню | Действие |
|---|---|
| 1. Добавить животное | Ввод → медосмотр → приёмка или карантин |
| 2. Добавить предмет | Ввод названия и инвентарного номера |
| 3. Отчёт по питанию | Расход корма по каждому животному + итог |
| 4. Контактный зоопарк | Травоядные с добротой > 5 |
| 5. Инвентаризация | Все животные и предметы с инв. номерами |
| 0. Выход | — |
